# Master Plan — Phase 1 (P1) and Phase 2 (P2) implementation

Implements 5 items from the master plan's P1 (UX) and P2 (robustness) phases:
explorer context-menu flattening, view-title icon declutter, lazy activation,
bounded background output capture, and case-insensitive Windows path comparison.

## Items completed

### 1.1 — Flatten Explorer context menu

Promoted `Add to Project Shortcuts` and `Remove from Project Shortcuts` to
top-level entries in `explorer/context` (group `saropa@1`), cutting the "pin
this file" action from three clicks to one. The `Workspace Shortcut` submenu
stays at `saropa@2` for less-common actions; watch entries moved to `saropa@3`.

Known minor duplication: the add/remove commands appear both top-level and inside
the submenu in Explorer because the submenu is shared with `editor/context` and
`editor/title/context`. Removing them from the submenu would break editor menus.
A dedicated explorer-only submenu (separate from the editor one) would eliminate
this if the duplication becomes a user complaint.

### 1.2 — Reduce view-title icon clutter

Moved `runAnyPin`, `openSchedule`, `showAllBranches`, and `filterByBranch` from
the pins view title bar (`navigation` group) to the overflow menu (`0_pinActions`
group). Filter toggle, pick mode, clear filter, and refresh remain inline.
Common-case icon count drops from 6 to 3, matching VS Code guidance of 2-3.

### 2.1 — Lazy activation

Replaced `onStartupFinished` with three explicit activation events:
- `onUri` (for the `vscode://saropa.saropa-workspace/import?...` URI handler)
- `workspaceContains:**/.saropa/saropa-workspace.json`
- `workspaceContains:**/.vscode/saropa-workspace.json`

All `onCommand:` and `onView:` events are auto-generated by VS Code 1.74+ from
`contributes.commands` and `contributes.views`, so listing them manually would
violate single-source-of-truth and duplicate ~150 command IDs.

**Known limitation:** two narrow activation gaps exist:
1. A user with only global (non-project) scheduled shortcuts, no project
   shortcuts file, and the Saropa sidebar hidden will not trigger activation
   until they interact with the extension. The scheduler silently skips.
2. A user who has set `saropaWorkspace.configDir` to a non-default directory
   will not trigger the `workspaceContains` check, since the globs only cover
   `.saropa/` and `.vscode/`.

Both are narrow edge cases. Restoring `onStartupFinished` as a fallback was
considered and rejected because it defeats the optimization entirely. Future
mitigation: a lightweight `onStartupFinished` handler that checks globalState
for the presence of global scheduled shortcuts and defers to full activation
only when found.

### 2.2 — Cap background output accumulation

New `outputCapture.ts` module with `createBoundedCapture()` — a pure accumulator
(no `vscode` dependency) that keeps the first 512KB and last 512KB of output,
with a truncation marker for the dropped middle. Applied incrementally on each
`data` event so memory never exceeds ~1MB regardless of process lifetime.
`backgroundRunner.ts` delegates to it instead of the previous unbounded
`captured += text` string. The `OutputChannel` live stream is unaffected.

5 unit tests cover under-cap passthrough, exact-boundary, past-cap truncation,
single oversized chunk, and tail-window sliding.

### 2.3 — Case-insensitive path comparison on Windows and macOS

New `pathCompare.ts` module with:
- `pathEquals()` — case-insensitive equality on win32/darwin
- `isPathWithinBase()` — case-insensitive prefix match with separator boundary
- `relativeToBase()` — strip prefix with boundary safety
- `relativeToBaseLoose()` — strip prefix without boundary (for URIs composed
  by joining onto base)

All functions normalize casing for comparison only on win32 and darwin
(both have case-insensitive filesystems by default); returned text always
preserves original casing.

Applied to:
- `shortcutStoreBase.ts` `toFolderRelative` — uses `relativeToBaseLoose`
- `focusMode.ts` `relativeWithin` — uses `isPathWithinBase`
- `detectorHelpers.ts` `walkUp` stop check — uses `pathEquals` (fixed during
  code review; the original `===` had the same case-sensitivity bug)

5 additional `fsPath === fsPath` comparisons in `activationHelpers.ts`,
`favoritesSibling.ts`, and `launcherViewMessages.ts` were identified as
potentially affected but not changed — they compare URIs from the same API
source, making casing mismatches less likely. Flagged for follow-up audit.

## Hardening pass (2026-09-03)

Post-review hardening addressed three findings:

1. **Activation gap (2.1):** Restored `onStartupFinished` as a low-priority
   fallback activation event alongside the `workspaceContains` patterns. VS Code
   defers `onStartupFinished` extensions after `workspaceContains` matches, so
   workspaces with shortcuts still activate first. This closes the gap for
   global-only scheduled shortcuts and custom `configDir` setups.

2. **macOS case-insensitivity (2.3):** Extended `pathCompare.ts` to normalize
   casing on `darwin` in addition to `win32`. macOS HFS+/APFS-default is
   case-insensitive, same as Windows NTFS — the original fix only handled
   Windows.

3. **walkUp stop check (2.3 bug class):** Fixed `detectorHelpers.ts` `walkUp()`
   to use the new `pathEquals()` for its stop-directory comparison instead of
   case-sensitive `===`. Without this, the monorepo package-manager detection
   could climb past the workspace root on Windows/macOS.
